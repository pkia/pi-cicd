# Incident 2026-11-16 — every hostname stopped resolving (DNS), network fine

**Severity:** full outbound name resolution loss; Hermes could not reach any
model provider ("Unable to reach the model provider. You may be offline.").
**Duration:** ~23:35 → 00:07 GMT (recovery at 00:07, confirmed 00:08).
**Blast radius:** every tool that opens a hostname — Hermes gateway/photon,
apt, GitHub, ntfy by name, StreamHub EPG fetches, cron jobs.
Raw-IP traffic kept working the whole time, which is what made it look like a
provider outage rather than a local resolver failure.

## Symptom

| Check | Result |
|---|---|
| `ping 1.1.1.1` | OK |
| `ping google.com` | "Temporary failure in name resolution" |
| `getent hosts api.deepseek.com` | FAIL |
| `curl https://ipinfo.io/ip` (vpn-guard probe) | FAIL |
| Surfshark `wgsurf0` | up, handshake fresh, kill switch armed |

## Root cause

`eth0` is a **manual IPv4** NetworkManager profile (`Wired connection 1`,
192.168.0.7/24, gw 192.168.0.1) whose `ipv4.dns` was **empty**. NetworkManager
is the only writer of `/etc/resolv.conf` on this box, so it wrote a header-only
file:

```
# Generated by NetworkManager
```

No nameserver, no resolution. The static address and default route were
correct the entire time — hence ICMP to literal IPs passed while every name
failed.

## Resolution (applied by the owner, not by automation)

```bash
sudo nmcli connection modify "Wired connection 1" ipv4.dns "1.1.1.1 8.8.8.8" ipv4.ignore-auto-dns yes
sudo nmcli connection up "Wired connection 1"
```

`/etc/resolv.conf` then contained `nameserver 1.1.1.1` / `nameserver 8.8.8.8`.
Verified after recovery: Google hostname, Cloudflare DNS, Google DNS, Z.AI
(HTTP 301), `wgsurf0` still up, Hermes model path restored.

## Persistence across reboot

The DNS servers live inside the profile file
`/etc/NetworkManager/system-connections/Wired connection 1.nmconnection`
(`dns=1.1.1.1;8.8.8.8;`, `ignore-auto-dns=true`, `method=manual`,
`autoconnect=true`), so a reboot re-applies them: NetworkManager activates the
profile and regenerates `resolv.conf` from it. The owner's own
`nmcli connection up` proves the re-apply path.

Supporting negatives checked so boot cannot quietly diverge:

- `/etc/network/interfaces` is empty and `interfaces.d` has no eth0 stanza; the
  ifupdown plugin is `managed=false`. No second writer.
- `dhcpcd` is not installed.
- Exactly one eth0 profile exists in NetworkManager.
- No dispatcher script (`/etc/NetworkManager/dispatcher.d`), timer, cron job or
  systemd unit references `resolv.conf`, `resolvconf` or `nmcli ... dns`.

**Not empirically reboot-tested:** a reboot would drop the live WebUI session.
Treat reboot survival as verified-by-inspection, not by experiment.

## Why nothing caught it early (gap analysis)

- **vpn-guard** (every 2 min) probed `https://ipinfo.io/json`, so it *did*
  notice — "exit probe failed but handshake fresh (no leak possible: kill
  switch on)" at 00:02, 00:04, 00:06 — but it cannot distinguish a DNS failure
  from a Surfshark edge hiccup, and it is written never to treat that as a leak
  (correct, but blind to the real fault).
- **pi-doctor** has a DNS check, but it queries `127.0.0.1:53` and is gated on
  the `AdGuardHome` unit existing. AdGuard is not installed here, so the check
  is inert.
- **service-probe** only probed loopback/tailnet **IP literals**
  (dashboard, webui, ntfy) — nothing that needed a name, so it stayed 100% green
  through a total resolution outage.
- **hermes doctor** connectivity checks are hostname-based too: they fail, but
  they report the provider as unreachable rather than the resolver as broken.

## Preventative monitoring added

Two probe families in `/etc/service-probe.conf` (service-probe every 5 min,
`CONFIRM_FAILS=2`, alerts on the `services` ntfy topic — backup at
`/etc/service-probe.conf.bak-*`):

```
PROBE_HTTP=... ,egress-ip=https://1.1.1.1/cdn-cgi/trace,dns-system=https://cloudflare.com/cdn-cgi/trace
PROBE_DNS=dns-cf=1.1.1.1:53:api.deepseek.com,dns-google=8.8.8.8:53:api.deepseek.com
```

Diagnosis matrix:

| egress-ip | dns-cf / dns-google | dns-system | Meaning |
|---|---|---|---|
| OK | OK | DOWN | **local DNS config broken** (this incident) |
| OK | DOWN | DOWN | upstream resolver unreachable |
| DOWN | — | — | IP path down (tunnel / kill switch / link) |

- `egress-ip` uses a literal IP, so it exercises external routing with no DNS.
- `dns-system` resolves a hostname through libc, i.e. through the system
  resolver — the exact path that broke.
- `dns-cf` / `dns-google` send a raw A query straight at a public resolver,
  bypassing `/etc/resolv.conf`, which separates "our resolver config" from
  "DNS as a service is dead".

`pi-cicd/dns-check` is the on-console equivalent: read-only, prints the verdict
plus the recovery commands, exit 0/1/2/3 for healthy / DNS / egress / both.

## Potential causes of recurrence

1. The profile is edited back to `ipv4.method auto` or recreated without
   `ipv4.dns` (a fresh static setup typically looks exactly like the broken
   state).
2. `ipv4.ignore-auto-dns` reset to `no` while DHCP advertises nothing useful.
3. NetworkManager's DNS plugin switched (e.g. to `systemd-resolved`) in
   `NetworkManager.conf` — NM then stops writing `resolv.conf`, and
   systemd-resolved is not installed here.
4. A future `DNS=` line added to `wgsurf0.conf` **plus** `resolvconf` installed:
   tunnel restarts would begin rewriting `resolv.conf`, bypassing the NM profile.
5. `tailscale set --accept-dns=true`: Tailscale would take over `resolv.conf`
   (currently `CorpDNS: false`).
6. Deploying AdGuardHome on 127.0.0.1:53 without pointing the NM profile and
   `resolv.conf` at it — would bring back a local resolver that nothing uses.

## Outstanding risks

- Reboot survival verified by inspection only (see above).
- `dns-check` is installed as `~/.local/bin/dns-check` (symlink into this
  repo, 2026-11-16 00:54) and was executed by the daily audit at 06:31 with
  exit 0 — IP egress OK, `api.deepseek.com` resolving, verdict healthy.
- service-probe's alert text names the failing probe (`dns-system DOWN: Name or
  service not known`) but does not include the recovery commands; the runbook
  lives here and in the `homelab-vpn` skill.
- Resolver is public (1.1.1.1/8.8.8.8) with no local cache; a public-resolver
  outage on both providers is still a total resolution outage.
